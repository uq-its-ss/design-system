# Release Documentation and Changelog Generation Strategy

We use date-based GitHub Releases as the canonical source for stable release documentation, with an auto-generated root CHANGELOG.md for developer reference. This approach accommodates our independent package versioning (40+ packages with separate semver) while providing stakeholders with a unified "what changed" story.

## Context

The UQ Design System is a Lerna monorepo with 40+ independently-versioned packages. We publish two release types:

- **Alpha releases** (master branch): Multiple times per week, pre-release versions for testing
- **Stable releases** (releases branch): Monthly-ish, production-ready versions

**The problem:** With independent package versioning, there's no single "design system version" (e.g., @uqds/button@2.0.0, @uqds/header@1.5.3, @uqds/card@3.2.1 all ship together). Stakeholders across accessibility, analytics, UI, and Brand teams need a central way to understand what changed across the entire system, not just individual packages.

**Existing state:**
- Per-package CHANGELOG.md files (auto-generated by Lerna, often saying "Version bump only")
- No unified release documentation
- No GitHub Releases
- Squash merge to master (breaks multi-package versioning accuracy)

## Decision

### Release Naming: Date-Based

Use **date-based release titles** instead of semantic versioning for system-level releases:

- Format: `Release: YYYY-MM-DD` (e.g., "Release: 2026-08-31")
- Multiple releases same day: append sequence (e.g., "Release: 2026-08-31.2")
- Git tags: `release-YYYY-MM-DD` and `release-YYYY-MM-DD.N`

**Rationale:** Individual packages use semver; the "design system" as a whole doesn't have a version. Date-based naming:
- Avoids confusion between package versions and system releases
- Matches how stakeholders think ("What changed in August?")
- Doesn't artificially escalate major versions when individual components break
- Natural chronological ordering

### Merge Strategy: Standard Merge (Not Squash)

Use **standard merge** for PRs to master branch (preserve all commits).

**Rationale:** Lerna's conventional-commits versioning reads individual commit types to determine version bumps per package. Squash merge creates ONE commit with ONE type, causing all changed packages to get the SAME version bump (incorrect for multi-package changes). Standard merge preserves granularity:
- `feat(header):` → header gets MINOR bump
- `fix(button):` → button gets PATCH bump  
- `feat!(card):` → card gets MAJOR bump

**Requirement:** All commits in PR must use conventional commit format before merge.

### Documentation Architecture

**Primary source of truth:** GitHub Releases (stable releases only)

**Workflow:**

1. **Alpha releases (master branch):**
   - Lerna auto-publishes with `--conventional-prerelease`
   - Creates git tags: `@uqds/package@version-alpha.N`
   - Publishes to npm with `@alpha` dist-tag
   - Updates per-package CHANGELOG.md files
   - **NO GitHub Release created**
   - **NOT included in root CHANGELOG.md**

2. **Stable releases (releases branch):**
   - Lerna dry run calculates versions
   - GitHub Action creates **draft GitHub Release** (when PR to releases is opened)
   - Manual approval gate (existing workflow)
   - **Human adds summary** (5-10 min): highlights, breaking changes, migration notes
   - Lerna publishes with `--conventional-graduate`
   - Creates git tags: `@uqds/package@version` (per-package) + `release-YYYY-MM-DD` (release tag)
   - Publishes to npm with `@latest` dist-tag
   - **Publishes GitHub Release** (with manual summary + auto-generated details)
   - **Auto-generates root CHANGELOG.md** from all stable GitHub Releases

**Release notes format:**
- Manual summary at top (context, highlights, breaking changes with inline migration notes)
- Auto-generated categorized changelog below (grouped by change type: Features, Bug Fixes, etc.)
- Per-package CHANGELOGs continue to be maintained by Lerna (for npm package consumers)

### Commit Message Guidance

**Tools:** Commitlint + Husky (local git hook) + PR template + CONTRIBUTING.md

**Enforcement level:** Guidance, not blocking
- Git hook provides immediate feedback on commit format
- Developers can bypass with `--no-verify` if needed
- No PR-level blocking (team not comfortable with force-push workflow yet)

**Multi-package commit guidance:**
- Prefer atomic commits (one logical change per commit)
- For coupled changes of same type: use most-affected package as scope
- For 3+ packages: use generic scope (core, components, styles)
- List affected packages in commit body

## Considered Options

**Release naming alternatives:**
- **Semver meta-package:** Create @uqds/design-system package with its own version — rejected because version number would be arbitrary (when is button@2.0.0 + header@1.5.3 = system@2.0.0 vs system@1.6.0?)
- **Calendar versioning (CalVer):** v2026.08.0 format — rejected as unnecessarily version-like when packages already have real versions
- **Manual milestone versions:** Only release at major milestones (v2.0 "Accessibility Overhaul") — rejected because we publish monthly, would create large gaps

**Merge strategy alternatives:**
- **Squash merge with conventional PR titles:** Would require choosing one change type per PR, losing granularity for multi-package changes
- **One package per PR policy:** Unrealistic for this codebase where changes frequently span packages (e.g., header + footer + navigation)

**Changelog architecture alternatives:**
- **Manual maintenance of both:** GitHub Releases + root CHANGELOG.md separately edited — rejected as duplicate work prone to desync
- **Generate GitHub Release FROM CHANGELOG.md:** Root file as source of truth — rejected because stakeholders prefer linking to web pages, and GitHub Releases have richer features (attachments, discussions)
- **Per-package CHANGELOGs only:** No unified view — rejected because stakeholders need system-level "what's new" story

**Alpha release handling alternatives:**
- **Create GitHub Releases marked as pre-release:** Would clutter releases page with dozens of alphas per month
- **Weekly alpha rollup releases:** Aggregate week's changes — rejected as delayed release notes don't match actual publish cadence

## Consequences

**Positive:**
- Stakeholders get unified, linkable release documentation (GitHub Releases)
- Accurate per-package versioning (Lerna conventional-commits works correctly)
- Developers get local CHANGELOG.md for offline reference
- Breaking changes are per-package, clearly labeled with migration notes
- Single source of truth (GitHub Releases) auto-syncs to root CHANGELOG.md
- Alpha releases stay fast and automated (no manual overhead)

**Negative:**
- Requires team discipline to write good conventional commits (mitigated by git hooks)
- 5-10 minutes manual work per stable release to write summary (accepted trade-off for cross-team communication value)
- Standard merge creates messier git history than squash (accepted for versioning accuracy)
- Date-based releases feel less "version-like" (mitigated by packages having real semver)
- Manual cleanup of orphaned draft releases if PRs close without merging (rare, acceptable)

**Risks:**
- Team might forget to edit draft release before approval → release published with only auto-generated changelog (graceful degradation, can edit after publishing)
- Developers might bypass commit hook frequently → inconsistent commit messages (monitor via PR reviews)
- Root CHANGELOG.md gets out of sync if GitHub Release API changes or automation breaks (recoverable: regenerate from API)

## Status

Accepted (2026-08-31)
